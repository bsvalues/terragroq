--- THE MEASUREMENT THIS LANE GOT WRONG ---------------------------------------------------------

Recorded because it was one commit away from shipping, and because it is this program's own
signature failure committed by the lane that keeps naming it.

While reading the test harness, this lane ran it and read exit=0 from a shell pipeline:

    powershell.exe -NoProfile -File test-crossnode-sync-receipt.ps1 2>&1 | head -40; echo $?

and concluded the harness could fail while reporting success -- "a test suite whose failure signal
does not reach its caller". A fix was written, with a comment block asserting that both 5.1 and 7
return 0 on an uncaught terminating error.

The measurement was of `head`, not of PowerShell. `$?` after a pipeline is the last element's
status. Re-measured without the pipe, capturing the process's own exit:

    out=$(powershell.exe -NoProfile -File exitprobe.ps1 2>&1); echo $?     -> 1
    out=$(pwsh          -NoProfile -File exitprobe.ps1 2>&1); echo $?     -> 1
    out=$(pwsh -NoProfile -File test-crossnode-sync-receipt.ps1 2>&1)     -> 0, PRODUCER_TESTS_PASS

Both shells signal failure correctly and the harness passes at 0. The record's LC-01 line was right
and the finding was not. The change was reverted before commit; only the IdentitiesOnly and -n
assertions remain in that file.

A second reading of exit=9, from `& $script` inside an interactive pwsh session, was also an
artifact: $LASTEXITCODE there is left over from the deliberate `cmd.exe /c exit /b 9` negative test
inside the harness, and it is not the exit code the script returns under -File.

Same class as the F: literal, one layer up: a value read from the wrong place, believed because it
was measured rather than because it was measured correctly.
