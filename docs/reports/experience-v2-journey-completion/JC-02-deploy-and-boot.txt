The start script's whole mechanism is that DATABASE_URL set in the child's environment beats the

An earlier run of the same probe reported INCONCLUSIVE_NO_CONNECTION_OBSERVED with the app
reporting ECONNRESET at 7ms -- i.e. it had plainly connected to one of the two listeners. The
listener was totalling its counts and writing them at exit, and Stop-Process on Windows terminates
rather than delivering SIGTERM, so the writer never ran. Evidence that exists only if a process is
shut down politely is evidence that goes missing exactly when something has gone wrong. It now
appends per connection. The first number is recorded because a reader would otherwise find it.

=== 4. the deploy that aborted, and what it cost ===
The first run stopped the task, captured the rollback, replaced the bundle, placed the boot tooling,
and then THREW on its own resolution check -- leaving the service down. The check had succeeded:
its output was the resolver's diagnostic naming host 192.168.88.8.

Windows PowerShell 5.1 wraps anything a native command writes to stderr in a NativeCommandError
record regardless of exit code, and $ErrorActionPreference = "Stop" makes that terminating. The
resolver writes its evidence line to stderr BY DESIGN. So success is what killed it. Redirecting to
a file (2>$path) does not help; only lowering the preference around the call does.

The same defect then refused the boot itself: LastTaskResult 1, an empty boot log, and a diagnostic
naming .8. Both call sites now drop to Continue for the invocation, restore the previous preference
in a finally, and read the verdict from $LASTEXITCODE -- which is the only thing that was ever a
verdict. Guarded by tests at both sites.
