Captured on HERMES 2026-08-25T03:13:00.

With the container republished and both policy layers admitting HERMES, the settlement
driver still reported AUTHORITY_UNREADABLE. The transport was fine; the error was
  { message: "password authentication failed for user \"williamos\"", code: "28P01" }

=== first, the resolver was ruled out as the cause ===
The resolver re-serialises the URL through node's URL parser, which could plausibly
re-encode a password. It does not:
  raw password in the file          len=64  sha256[0:16]=53fe7af08e6d3c24
  after URL parse                   len=64  sha256[0:16]=53fe7af08e6d3c24
  after registry host substitution   len=64  sha256[0:16]=53fe7af08e6d3c24
  only the host changed: 192.168.88.5 -> 192.168.88.8

=== the role's stored verifier is scram-sha-256, and so is the policy ===
  so this is not a mechanism mismatch. The credential itself is simply not the role's.

THE FINDING. The credential in the LIVE runtime's .env.local is not the williamos role's.
The deployed WilliamOS runtime on HERMES therefore cannot read the authority registry
even now that the transport is restored -- every governed route it serves would refuse
AUTHORITY_UNREADABLE. This lane did not repair it: changing the live runtime's
configuration is outside a reads-and-driver-run boundary and would require restarting a
service other lanes may be using. Typed as CONT-EXPV2-RUNTIME-CREDENTIAL-STALE.

This lane's own runs sourced the credential from the file proven above and resolved the
HOST from the fabric registry. No password was changed, printed, or copied anywhere.
